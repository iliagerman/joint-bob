Dashboards

Design for approval. Nothing is built until you approve this. Full text: docs/superpowers/specs/2026-10-24-dashboards-design.md

What it is

Live dashboards inside Joint Bob. You describe a dashboard to a creator agent, and it builds one: a data script (or an AI refresh), plus a displayable HTML page. Dashboards exist at three levels: conversation, project and workspace, and each entity can hold several, with one visible at a time.

First use case, for Contigos: bugs per day, errors per day, and bugs by type, so a fix can be checked. Joint Bob provides the infrastructure and the creator agent. Each dashboard carries its own data logic.

Architecture (summary)

Storage
  • Records in the node's SQLite.
  • Files in the node's app folder, one per dashboard: definition, state/ for script history, last payload, run log.
  • Not in the project folder: sync excludes .joint-bob/, and dashboards are node-local.
Display
  • Sandboxed iframe, no same-origin access, no network.
  • Data passed in as JSON; refresh reloads the frame.
  • One narrow frame allowance in the app's CSP, for this route only.
Controls
  • One vendored, permissive chart library, pinned in the repo.
  • Joint Bob components: KPI tile, time series with event markers, bar, stacked bar, donut, heatmap, paged table, badges, text, grid, states.
  • The creator prompt forbids other libraries and outside URLs.
Sharing
  • Definition only: never payloads, state, logs or creator transcripts.
  • Modelled on saved commands (per-receiver manifest) and skill sharing (validated bundles).
  • Owner updates replace the received copy; local edits fork a local copy.

Calls I made (you can change them)

  • Previewing a received dashboard shows layout and empty states only. It never runs the received script or AI refresh.
  • Multi-user access: anyone who can open the entity can view its active dashboard. Creating, editing, refreshing, sharing and deleting need the right to run agents there. A workspace dashboard's script runs as the workspace owner.
  • Timeouts, output size and run-log limits are left to the builder, with defaults around 2 minutes and a few MB.

Three decisions for you

A reviewer read the design and found these three open. My recommendation is in each. Approve the recommendation, or tell me what to change.

Your callRecommended
1. Which node runs a dashboard when the page and the project are on different machines?
Example: you browse on the Mac, and the Contigos project runs on the homeserver. The answer decides which secrets and project copy the script uses, and where its history is kept.
Recommended: the node that owns the entity runs it. The Mac displays the result, the same way conversations already run on their owner.
Your callRecommended
2. Must you approve a received script before it runs, and again on every change?
A received script runs on your node with that project's secrets. Without approval, a sender's update could run new code on your next Refresh.
Recommended: yes. Approval is asked when you first activate a received dashboard, and again after any change to its script. Until approved it shows its layout only.
Your callRecommended
3. Should a twin show a received dashboard automatically when it has none of its own?
Example: you build a dashboard on the homeserver, then open the same project on the Mac. As written, the Mac shows "describe your dashboard" until you activate the received one.
Recommended: yes for twins. It becomes active when the twin has no dashboard of its own, and stays inactive when it does. Non-twin nodes keep the inactive default.
