Feature · Multi-node

Clusters, sharing, and twins

A Joint Bob node can belong to any number of clusters. Membership alone shares nothing: a node shares chosen projects or whole workspaces with a cluster, and every member of that cluster receives them. Twins are the same user's machines and share everything they own. Changes travel through two hubs per cluster, and a twin can take over a machine that is gone for good.

How It Works

Sharing

  1. 01
    Membership
    Every node creates an Ed25519 identity. A cluster's manager signs the member list; members are numbered by join order. A node can be a member of any number of clusters and presents one URL to all of them.
  2. 02
    What a peer may see
    A peer sees a project if it is a twin of the project's owner, or it shares a cluster with the owner and the owner selected the project (or its workspace) for that cluster. Every member of that cluster receives it. Data outside any project, canvas shortcuts, push subscriptions, and ntfy servers go to twins only.
  3. 03
    Isolation between clusters
    A node in clusters X and Y shares each project only with the cluster it selected. Members of X and Y do not learn about each other and cannot authenticate to each other.
  4. 04
    Twins
    Twins are the same user's machines. Both sides consent; afterwards each shares everything it owns with the other: projects, conversations, tasks, files, transcripts, credentials, routing configurations, and update rights.

Two-hub dissemination

  1. 01
    Hubs
    For each cluster, the node that makes a change sends it only to two hubs: the lowest and the highest numbered other members that answer. If a hub does not answer, the next member in line takes its place.
  2. 02
    Forwarding
    A hub applies the change and forwards it to every other member of that cluster that may see it. Each relayed event carries its origin's signature; a hub cannot forge or alter it.
  3. 03
    Catch-up
    Every node keeps each cluster event it holds in a relay log. At start-up and every minute a node pulls everything after its cursor from the two hubs, so a node that was offline, or missed a forward, catches up. A project shared with a cluster later sends its earlier events once.
  4. 04
    Twins
    Twins keep direct delivery. A cluster whose other members are all twins of this node needs no hubs.

Recovering a lost machine

  1. 01
    Declare it lost
    On a twin of the lost machine, open Settings > Cluster, choose the twin, and select This machine is lost. Only a twin can do this: the dual-signed twin certificate proves the lost machine trusted it.
  2. 02
    Ownership moves
    The twin becomes the owner of everything the lost machine owned and reissues its sharing. Other members verify the certificate against the keys they already hold and accept the twin as the new owner.
  3. 03
    Clusters
    The manager removes the lost machine. When the lost machine was the manager, the most senior remaining member takes over management and removes it.
  4. 04
    Rebuild
    Install Joint Bob on the new or repaired machine and pair it as a twin with the survivor. It receives everything again. Invite it to its clusters again.
A lost manager without a twin
A cluster whose manager is lost and had no twin cannot choose a new manager. Keep the machine that manages a cluster twinned with another machine you own.

Access Control

  • •Every machine request is signed and checked against the sender's pinned key, a 60-second clock window, and a replay-proof nonce. Bearer machine tokens are no longer accepted anywhere.
  • •Runtime calls are authorized by the project they name. A request for a project that is not shared with the caller returns 403.
  • •Relayed events are accepted only with a valid origin signature, from a member of the cluster, for a project the receiver, the origin, and the sender may all see.
  • •Only the lost machine's twin can succeed it. A succession notice from anyone else returns 403.
  • •Remote update installation requires an active twin.
  • •A connection that fails on malformed data closes that socket only; it never stops the node.

Upgrading

  • •Update every node of a cluster to this release. Older nodes do not relay or pull, and reject member lists with more than five members.
  • •Legacy bearer-token pairing is removed. A node that still has a legacy pairing loses it and must join through a cluster invitation or pair as a twin.
  • •A node older than 1.59.0 must first upgrade to a release between 1.59.0 and 1.97.x.
  • •The retired pairing tables are dropped on start; the node keeps its identity.

Known limits

  • •Relay logs and the event outbox are not pruned yet.
  • •Shared agent skills (the agent-resources Syncthing folder) do not synchronize between nodes.
  • •A node advertises one URL to all its clusters, so every cluster must reach it at that URL.
  • •Tasks still assigned to a lost machine keep that assignment until they are handed off.
